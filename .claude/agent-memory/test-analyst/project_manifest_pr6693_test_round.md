**Real findings reported to team-lead 2026-09-24:**
1. Golden/Manifest.hs's new "unsupported schema version rejected" check (from `aaa72e7380`, in-scope of the diff even though not one of the 3 named commits) uses a manual `case eitherDecode v2 of Left _ -> pure (); Right _ -> failure` instead of `H.assertWith isLeft` - violates the no-manual-case-match convention and loses the diagnostic value of `noteShow_` (the wrongly-decoded `Right` value isn't shown on failure).
2. `hprop_manifest_windows_pipe_path`'s SECOND assertion (`makeManifestRelPath outputDir pipePath === pipePath`, calling the real function under ambient - Posix on Linux - `System.FilePath`) is empirically NOT a meaningful Windows regression guard on the ubuntu/macos CI legs: verified with a throwaway `runghc` script that Posix's `makeRelative`/`normalise` pass this backslash-only string through unchanged for ANY base directory, not because of Windows drive semantics but because Posix has no separator concept for backslashes at all (structurally different reason than the Windows flavour's `splitDrive` drive recognition, which the doc-comment's "checked on filepath 1.4.301.0, both flavours" phrasing conflates as one explanation). Net coverage across the full CI matrix is fine, since `.github/workflows/haskell.yml` has a `windows-latest` leg and assertion 2 becomes the genuinely meaningful one there (ambient = Windows) while assertion 1 covers Linux/macOS - so not a functional gap, just a misleading comment.
3. Real coverage gap: `removeStaleManifest` has two call sites in `Testnet/Start/Cardano.hs` (`createTestnetEnv` at line ~137, `cardanoTestnet` itself at line ~272, per [[manifest_json_pr6693]]). The new stale-manifest test only exercises the `createTestnetEnv` site. The `cardanoTestnet`-only site (relevant to the `StartFromEnv` CLI path reusing an existing environment dir) is only ever reached today via `createAndRunTestnet`'s double-call (`createTestnetEnv` then `cardanoTestnet` in the same dir, `Testnet/Start/Cardano.hs:613-615`), where the file is already gone by the time `cardanoTestnet`'s own call runs - so a regression at that second call site would go undetected by every existing or new test.

Useful technique: verified filepath cross-flavour claims empirically with a throwaway `runghc` script importing `System.FilePath.Posix`/`System.FilePath.Windows` qualified, rather than trusting a doc-comment's claim - GHC and the `filepath` package are available in the sandbox even without a project build.

**Follow-up round (same day): Windows/wine thread.** Team lead asked me to check a review-thread claim that un-gating `hprop_manifest`/`hprop_manifest_stale` on Windows fails on Hydra's wine cross leg with `WSAENOPROTOOPT` (build 14742303). Fetched the raw log at `https://ci.iog.io/build/<id>/nixlog/1/raw` with `curl -sL` (WebFetch's own AI-summary paraphrased a source location as "Manifest.hs:614" when the real callstack line was `src/Testnet/Start/Cardano.hs:614` inside `createAndRunTestnet`/`createTestnetEnv` - always cross-check WebFetch summaries of Hydra logs against the raw log for exact locations/line numbers).
Ground truth from the raw log: in that build, `hprop_manifest`/`hprop_manifest_stale` were NOT `ignoreOnWindows`-gated (unlike literally every other of the ~50 node-starting tests in `cardano-testnet-test.hs`, all shown "IGNORED on Windows"/"IGNORED on MacOS and Windows" in the same run) and both failed identically with `Network.Socket.setSockOpt: failed (Bad protocol option (WSAENOPROTOOPT))` inside `createTestnetEnv`/`cardanoTestnet`'s node-socket setup - nothing in `Testnet/Manifest.hs` itself. Meanwhile `hprop_manifest_windows_pipe_path` (the pure test, never gated) ran on the real mingw32-cross/wine binary and passed ("OK ... passed 1 test") - direct empirical proof the pure Windows-flavour test is NOT vacuous on the actual Windows target, confirming [[manifest_json_pr6693]]'s "essentially every other node-starting integration test is ignoreOnWindows" pattern is a pre-existing, general wine/mingw32 winsock limitation, not manifest-specific. At current HEAD both integration tests ARE gated (unchanged in the reviewed diff range), so build 14742303 must be a superseded/since-amended revision - PRs get force-pushed, and Hydra check-runs pin to a specific SHA (AGENTS.md's Hydra gotcha) so an old build's SHA can vanish from visible history entirely.

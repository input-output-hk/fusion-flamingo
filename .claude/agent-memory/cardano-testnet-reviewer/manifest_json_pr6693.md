PR #6693 added `Testnet.Manifest` (cardano-testnet/src/Testnet/Manifest.hs): `cardano-testnet cardano` writes `<output-dir>/manifest.json` once, atomically (temp file in the same dir + rename), after readiness checks pass, as a machine-readable "the cluster is ready" signal for scripts.
Schema at cardano-testnet/schemas/manifest.schema.json (draft 2020-12, `additionalProperties: false`); README section "Machine-readable interface" documents it as a stability-promised contract.

Architecture: `removeStaleManifest` runs unconditionally at the very top of `cardanoTestnet` (Testnet/Start/Cardano.hs:264) - this alone guarantees every path through `cardanoTestnet` starts clean.
`buildManifest`/`writeManifest` run near the end of `cardanoTestnet` (Cardano.hs:501-505), after block-production waits, wallet UTxO queries and `assertExpectedSposInLedgerState`.
Public API (`Cardano/Testnet.hs`) re-exports only the Manifest data types and pure constants, never the IO functions - "only cardanoTestnet writes the file" is enforced at the module boundary, a good pattern to point to in future reviews of similar features.

Both gaps below (reported to team-lead 2026-09-17) were VERIFIED FIXED on re-review 2026-09-18, commit 5b6c2582ad "write the manifest last, cover all entry points" (head 5a76c6794b on the PR branch):
1. Write ordering: FIXED. `buildManifest`/`writeManifest` now run after `when enableNewEpochStateLogging $ TR.startLedgerNewEpochStateLogging ...`, immediately before `pure runtime` - genuinely the last fallible step (Cardano.hs:507-515 at head 5a76c6794b). Moving it did not change what data is captured: pid is still `Process.getPid` at manifest-build time (unchanged relative order to writeManifest, just a few IO actions later in wall-clock terms).
2. Stale-manifest coverage: FIXED. `removeStaleManifest` now runs at the top of BOTH `createTestnetEnv` (Cardano.hs:137) and `cardanoTestnet` (Cardano.hs:272) - covers all 4 entry points: `NoUserProvidedEnv` CLI (createTestnetEnv + cardanoTestnet, double-covered harmlessly), `StartFromEnv` CLI (cardanoTestnet only, covered by its own call), standalone `create-testnet-env`/`createEnvOptions` (createTestnetEnv only, covered), `createAndRunTestnet` library wrapper (both, double-covered harmlessly). `removeStaleManifest` is idempotent (`doesFileExist` guard), so double-calls are not a bug.

Same fix commit also threaded the (possibly timestamp-updated) `ShelleyGenesis` through as a return value from the `updateTimestamps` branch instead of re-reading the file for the manifest's `systemStart` - correct and identical behaviour when timestamps are NOT updated. NOTE: the commit message claims this also fixes `chainForecastHorizon`/`chainStallWatchdog` seeing "updated stamps" - this is not actually true/needed: `chainForecastHorizon` (Testnet/ChainWatchdog.hs) only reads `sgSlotLength`/`sgSecurityParam`/`sgActiveSlotsCoeff`, never `sgSystemStart`, and the `updateTimestamps` QoL feature never touches those three fields. So the pre-fix code (still on origin/master) reading the stale `shelleyGenesis` binding for the forecast horizon was harmless dead-staleness, not a real bug; only the manifest's `systemStart` field actually benefited from the fix. Minor commit-message inaccuracy, not a functional issue.

The pid-description schema inaccuracy flagged previously was ALSO fixed independently, in commit 1f16031e63 ("keep the manifest schema strict, fix the policy text"): schema now says "captured at the time the manifest was written ... pid recorded at node start time is in the pid file."
Hardcoded path templates for `mnodePidFile`/`mnodeTopologyFile` were ALSO fixed, in commit e7d550de75: both now come from shared `Cardano.Node.Testnet.Paths` helpers (`defaultNodePidFile`/`defaultNodeTopologyFile`/`defaultNodesDataDir`, added there), used by both Manifest.hs and the real runtime path in Testnet/Runtime.hs:143 (pid file) and Start/Cardano.hs (topology file, in 3 places) - verified the shared constants compute byte-identical paths to the old per-site hardcoded literals, so this was a pure drift-elimination refactor with no behaviour change.

The Windows named-pipe guard in `makeManifestRelPath` (previously an explicit `\\.\pipe\` prefix check) was REMOVED in e7d550de75, relying on `System.FilePath.makeRelative`/`normalise` passing such paths through unchanged (matches [[filepath_windows_pipe_passthrough]] if that memory exists, or the AGENTS.md filepath gotcha).
Re: the Windows-testing question raised in review (carbolymer/palas thread) - the GOLDEN test (`golden_Manifest`) is fully synthetic: it hand-constructs a `sampleManifest` Haskell record with literal path strings (e.g. `"socket/node1/sock"`) and never calls `buildNode`/`makeManifestRelPath` at all, so it is platform-independent by construction and would produce byte-identical output on Windows and Linux regardless of the pipe-path guard. palas's claim that "the golden file would differ" on Windows does not hold for this specific golden test. The only path that would ever exercise `makeManifestRelPath` with a real Windows named pipe is the full integration test `hprop_manifest`, which is `ignoreOnWindows` - consistent with essentially every other node-starting integration test in `cardano-testnet-test.hs` (not a new or manifest-specific exemption). A real Windows test would need `hprop_manifest` itself un-skipped, not a golden-file variant.

**New findings from the re-review (not blocking, worth flagging):**
1. `check-mainnet-config` is NOT in branch protection's `required_status_checks` on master (contexts are `check-cabal-files`, `build-complete`, `ci/hydra-build:required`; verified via `gh api repos/IntersectMBO/cardano-node/branches/master/protection`, and no repo rulesets exist to add it either). So folding the manifest check in there does not make it a blocking/required gate - the commit message's "gates pushes and the merge queue" is optimistic; it runs and reports but doesn't hard-block merge either way.
2. Trigger-coverage asymmetry: `check-mainnet-config.yml` uses `on: push, merge_group` with NO `pull_request` trigger, unlike the repo's other three dedicated `check-*.yml` workflows (`check-cabal-files`, `check-git-dependencies`, `check-hlint`), which all use `on: pull_request # Required for workflows to be able to be approved from forks`. Consequence: for a fork-based external-contributor PR, `check-mainnet-config` (and now the manifest validation riding inside it) would NOT run during ordinary review at all - only at `merge_group` time, right before merge. Moot for PR #6693 itself (verified via `gh api .../pulls/6693`: `head.repo.fork: false`, same-repo branch, so the `push` event fired normally and the step ran/passed) but a real latent gap inherited by the fold-in for any future fork PR touching only the schema/Manifest.hs/golden file.
3. No `paths:` filter on `check-mainnet-config.yml` (never had one) means it DOES unconditionally run on every push/merge_group regardless of what changed - so the specific "will it trigger on a schema-only change" concern is answered YES, empirically confirmed by the live run. Downside is cost/naming, not correctness: every push pays for a heavy `nix build .#hydraJobs.cardano-deployment` just to reach the new lightweight jsonschema step, and a red "Check mainnet configuration" for a manifest-schema regression is a confusing name mismatch.
4. Recommendation given to team-lead: lean toward a dedicated `check-testnet-manifest.yml` modeled on `check-cabal-files.yml`'s `pull_request`+`merge_group`+`permissions` pattern instead of the fold-in - better trigger coverage (works on fork PRs during review, not just at merge time) and clearer naming, and the CodeQL permissions objection that reportedly killed that approach earlier is trivially satisfied by the same 3-line `permissions: contents: read` block already added to check-mainnet-config.yml in this PR. Counter-argument in favour of the current fold-in: reuses the nix-install step already paid for by check-mainnet-config.yml, saving ~20-30s per run. This is a nit/style call, not a merge blocker - current wiring is empirically verified working end-to-end.
